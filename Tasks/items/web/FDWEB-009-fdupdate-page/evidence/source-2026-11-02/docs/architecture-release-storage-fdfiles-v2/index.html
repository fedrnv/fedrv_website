FDUpdate release storage architecture — FDFiles protected object interface

Status: owner-directed successor for FDU-EPIC-D010 implementation. The accepted v1 S3 architecture remains immutable historical input.

Boundary

FDUpdate uses the versioned FDFiles v1 integration API as its primary protected store/read boundary. FDUpdate does not receive S3 credentials, bucket names, provider object keys or storage-placement authority. A short-lived service token is supplied by an external secret provider and is sent only to the configured HTTPS control origin.

The implementation is pinned to FDFiles wire version 1 and canonical OpenAPI SHA-256 38dc1b30cbff265d6944f1b37e9168cba64a9155f058a04d131ab85d573e2bf8. That contract belongs to the accepted FDFiles D040 product candidate 932daf9b9d3d1e6075dd6dc490c2b8f0c9557bfd (tree 2d392f1027b0efd5dec89b5333b6e7f673179ade) and was inspected read-only in the FDFiles repository. Its D040 gate and independent review are closed. The public FDFiles origin/main still points to the earlier 9328891 contract and is not deployment-compatible with mirror deletion; production configuration must use an accepted FDFiles build containing D040 or a compatible successor.

The unpublished prototype SDK is not copied or linked: its repository license allows packaging metadata only and forbids distribution without owner approval. FDUpdate implements the bounded HTTP operations required by this architecture.

Service-token issuance follows the normative OpenAPI scopes, not older prose: uploads require resources:write, resource reads and download sessions require resources:read, revision-bound deletion requires resources:delete, and all durable-operation polling requires operations:read. FDUpdate requests these exact scope identities from its external token source and requires separate protected regular token files for least-privilege operation. It does not use the obsolete files:read or files:write names. Different spellings of one path are canonicalized before the CLI accepts them as separate scope files.

Immutable identity

Every stored artifact is identified by its SHA-256, exact byte length, media type and the SHA-256 of the signed release manifest that authorizes it. The portable content key is sha256/<first-two-hex>/<full-digest>. FDFiles resource and revision IDs are opaque locators, never authority or artifact identity.

Publication creates a checksummed upload session, transfers bounded chunks, completes the session and accepts only a returned resource whose size and digest match the immutable identity. Retrieval pins the exact resource revision in a download session, validates range responses and verifies the complete digest before atomic activation by a caller.

Security and failure behavior

  • Control and data clients reject redirects. Authorization is sent only to the

    • control origin; data-plane requests receive only the headers returned for the exact capability URL.

  • Production origins require HTTPS. Plain HTTP is allowed only for an explicit

    • loopback test configuration.

  • Requests, retries, chunks, responses, operation polling and total artifact

    • size are bounded. Uncertain mutations retain stable idempotency keys.

  • Authentication, authorization, version, revision, size and integrity failures

    • fail closed and never create a trusted locator.

  • The local backend uses the same identity contract and atomically installs a

    • verified content-addressed file without following links.

Revision-bound deletion and remaining distribution boundary

Accepted FDFiles D040 resolves the earlier resource-delete contract gap. DELETE /v1/resources/{resource_id}?revision=... requires a stable Idempotency-Key and a resources:delete token. A stale revision fails without admitting deletion. FDUpdate accepts completion only from the exact durable delete_resource operation, polled with operations:read; retries use a key derived from the journal operation and exact opaque locator. The SDK licensing boundary remains, so no FDFiles package is distributed or linked.

FDU-141 does not delete resources. Its fdupdate-storage publish-stage CLI publishes one verified artifact to primary FDFiles, retrieves it through a read-scoped download session into an immutable VPS content object, then atomically advances a per-product/channel/platform/architecture/variant index. The prior index target remains the known-good fallback. Configuration names separate read_token_file, write_token_file and operations_read_token_file; all must be protected regular files outside the repository. A primary success followed by cache failure is reported as failure and is safe to retry under artifact-derived idempotency keys.

Delayed mirror mutation journal

FDU-143 adds the canonical fdupdate/mirror-mutation-journal/v1 state. Each bounded operation records an immutable ID, create/replace/delete kind, exact primary artifact identity and FDFiles revision, expected mirror revision when applicable, policy version, primary confirmation time and a computed not_before exactly 24 hours later. The journal is atomically persisted behind a separate process lock, rejects symlinks, duplicate IDs, noncanonical state and files larger than 16 MiB, and caps entries at 100,000.

fdupdate-storage mirror-enqueue JOURNAL REQUEST.json records a confirmed primary mutation. Replaying an identical immutable request returns the existing operation; changed input under the same ID conflicts. Enqueueing never contacts or activates a mirror. fdupdate-storage mirror-status JOURNAL REQUEST.json returns either the operation selected by optional operation_id or the bounded complete journal, including durable state, attempts and an explicit failure classification.

fdupdate-storage mirror-execute CONFIG.json REQUEST.json is the only execution entry point. CONFIG.json must explicitly set enabled: true, provide distinct primary and mirror endpoint configurations and non-reused credential files, a real staging directory, the journal path and a separate protected regular authority_public_key_file. The executor never receives the authority private key. With enabled: false, the operation stays pending. Endpoint token files are optional in the common schema but the attempted HTTP operation fails closed unless its exact resources:read, resources:write, resources:delete or operations:read token file is configured.

FDU-180 replaces caller-authored revalidation assertions with fdupdate/mirror-decision/v1. The execution request contains only a canonical base64 payload and Ed25519 signature. The domain-separated payload binds a unique decision and trusted key ID, operation ID and kind, policy version, exact Primary and expected Mirror identities/revisions, authorization and deletion eligibility, retention and last-restorable-backup protection, issue time and expiry. The configured public-key document has schema fdupdate/mirror-authority-key/v1; unknown keys, noncanonical encodings and bad signatures fail before any remote request.

An initial decision must be issued after the full hold, be neither future nor expired and remain within five minutes of execution. Create and replace require the authoritative exact Primary and Mirror state, then download and verify the Primary bytes before a checksummed create or revision-bound replace. Delete requires authoritative Primary absence, explicit eligibility, no retention pin and confirmation that the object is not the last restorable database backup. Changed, unauthorized or protected work is rejected or durably cancelled without remote mutation.

Before remote mutation the journal records running, the decision ID, the digest of the exact signed envelope and not_issued. The FDFiles adapter then classifies the actual resource-mutation boundary as a definitive response or transport / accepted-operation ambiguity; the journal persists definitive_failure, acceptance_unknown or confirmed. A crash before that outcome is durably recorded remains fail-closed as not issued. FDFiles mutation keys make a proven ambiguous retry safe if the process loses the completion response.

An explicit successful FDFiles response whose operation kind, resource shape, locator/revision, size, digest or JSON protocol is invalid is neither confirmed success nor acceptance ambiguity. The adapter and journal persist explicit_invalid_response; even an incorrectly classified Unknown + Identity/Integrity/Protocol result is normalized to that outcome. It remains retryable only with a newly issued fresh exact-operation decision. The expired byte-identical exception additionally requires acceptance_unknown with an unavailable transport/observation failure, so an invalid explicit response cannot manufacture authority merely by being retried.

An expired byte-identical decision may be reused only for the same operation whose persisted outcome is acceptance_unknown. Primary retrieval failures, local preparation failures, definitive 4xx/conflict responses and legacy records without the outcome cannot spend expired authority; they require a new, fresh, independently signed exact-operation decision. Changed payloads and cross-operation replay remain rejected. A bounded remote failure records retryable_failure and increments the attempt count; success records the exact returned mirror locator, or no locator for deletion. Temporary verified primary copies are removed when the command exits. No production mirror, credentials or provider placement are created by this implementation.

Verified download fallback

FDU-142 adds an optional tiered download runtime to fdupdate-web. The release catalog remains the authorization authority: public and authenticated routes must authorize the exact project, release and SHA-256 before any storage lookup or network request. A separate bounded tier catalog maps that exact tuple to an immutable primary locator, an optional explicitly configured mirror locator and the product/channel/platform/architecture/variant VPS cache key.

The resolver tries primary FDFiles, then the configured mirror, then an exact current or previous known-good VPS cache entry. Every tier must reproduce the catalogued size and SHA-256 before the file is exposed. Failed and corrupt candidates are removed. The mirror is disabled when it is absent from both the catalog record and runtime configuration; this feature does not activate a production mirror.

VPS fallback is copied to an isolated spool file and served through the normal range-capable gateway. Its body owns a non-blocking concurrency permit until the response is dropped, enforces a configured byte rate, and participates in a sliding one-minute request limit. Spool files are removed on completion, disconnect and invalid range. Older releases are served from VPS only when the requested immutable identity is the exact current or previous retained entry; otherwise the gateway returns service unavailable without substituting a newer release.

The tiered runtime accepts only protected resources:read token files and bounded FDFiles clients. Production control origins remain HTTPS-only. Operators must configure catalog_file, vps_cache_root, spool_root, primary read settings and all three VPS limits; an optional mirror uses the same read-only contract. Startup rejects unsafe paths, zero limits and invalid catalogs.

Encrypted FDUpdate state backup and staging restore

FDU-144 adds the canonical fdupdate/encrypted-backup/v1 envelope and fdupdate/backup-catalog/v1 recovery catalog to fdupdate-storage. The backup input is a database-native or quiesced snapshot set, not arbitrary live files. Every request carries one stable generation marker and must contain database, release catalog and installation-registry roles; a WAL may be included. The marker is read before and after copying, every source must remain the same regular non-symlink file while copied, and every copied byte receives a SHA-256 entry in the authenticated snapshot manifest. The producer must advance the marker for each state transaction or create the inputs while the service is quiesced. The backup command fails closed if that consistency contract is not met.

The snapshot is encrypted in bounded 1 MiB chunks with XChaCha20-Poly1305. A random 128-bit nonce prefix plus a monotonic 64-bit chunk index gives every chunk a distinct nonce; the complete public envelope header and chunk index are additional authenticated data. The encrypted object identity covers its exact bytes, while signed_manifest_sha256 in the shared storage identity carries the authenticated snapshot-manifest digest for this non-release object. Backup key files contain exactly 32 bytes encoded as 64 hexadecimal characters, remain outside the catalog and envelope, cannot be reused as any FDFiles scoped token or snapshot input, and must be protected by the host ACL. Key loss is intentionally not bypassed: restore fails rather than weakening confidentiality.

fdupdate-storage backup-create CONFIG.json REQUEST.json creates or safely reuses an immutable local encrypted archive, verifies a complete decrypt in a disposable directory, writes it to Primary FDFiles with resources:write and operations:read, then records a mirror-create operation through the FDU-143 journal. The journal confirmation time is the successful Primary operation, so the mirror cannot execute before the mandatory 24-hour hold. Primary and mirror service credentials remain scope-specific. The bounded local recovery window retains at least two newest verified encrypted archives; pruning never deletes a Primary object or the catalog record, and interrupted pruning can only leave an extra local copy.

fdupdate-storage backup-restore CONFIG.json REQUEST.json downloads the exact recorded Primary resource with resources:read, verifies its encrypted object identity, authenticates and decrypts every chunk into a disposable directory, then verifies the manifest, role set, sizes and SHA-256 of every restored file. Only the fully verified directory is atomically renamed to a new RESTORE_ROOT/BACKUP_ID staging path. An existing destination is never replaced; activation or live database replacement remains a separate owner-controlled operation. backup-status CATALOG.json REQUEST.json exposes immutable Primary, mirror-queue, local-copy and last successful restore evidence for FDU-145.

The initial implementation accepts at most 128 inputs and 512 MiB of snapshot payload. It deliberately performs no live migration, key escrow, production provider provisioning, automatic Primary deletion or mirror activation. A 24-hour-delayed mirror can lag by at least a day and is not advertised as zero-loss recovery; database-native snapshots/WAL and the local recovery window remain required.

Replica, retention and restore health

FDU-145 adds a bounded offline scrub command and an owner-only rendering of its validated result. fdupdate-storage health-scan CONFIG.json REQUEST.json accepts an empty request and a configuration containing report_file, tier_catalog_file, vps_cache_root, mirror_journal_file, backup_catalog_file, staging_root, primary, optional mirror, thresholds and rates. The Primary and optional Mirror endpoints must be distinct and use distinct credential files. Scrubbing only reads remote objects, so each configured endpoint needs only the normative FDFiles resources:read service token; no documentation-only files:* scope is accepted. The local journal, rather than remote operations polling, remains the replication-state authority.

For every retained release and encrypted backup, the scrub downloads the exact immutable locator into a disposable staging directory and verifies size and SHA-256 through the normal storage client. It separately verifies current and previous VPS cache bytes, local encrypted backup archives, delayed mirror journal state and recorded restore timestamps. The resulting fdupdate/storage-health-report/v1 records explicit healthy, disabled, queued, running, retrying, failed, missing, not-retained, unauthorized, unavailable, corrupt and protocol-error states. It also records queue age and overdue counts, backup/restore age alerts, unique retained bytes, VPS free bytes, configured capacity thresholds and operator-supplied USD-micro/GiB storage and scrub-egress estimates. Rates are estimates, not provider billing data.

The report is atomically replaced, rejects symlinks, is bounded to 32 MiB and contains no bearer token, encryption key or plaintext backup content. fdupdate-storage health-status REPORT.json REQUEST.json validates and prints it. fdupdate-web may set storage_health_report_file; startup rejects an invalid initial report and /admin/storage-health reloads it on every request. Only an owner session can access the page. A report older than its embedded freshness threshold is prominently marked stale and makes no current-health claim; a missing or corrupt replacement returns service unavailable without partial totals.

The scrub includes a dry cleanup plan for files below the VPS cache's objects/sha256 directory that are not referenced as current or previous. fdupdate-storage cache-cleanup CONFIG.json REQUEST.json is the only cleanup entry point. Its request must repeat the exact cache-state SHA-256 and cleanup fingerprint from a fresh report, set explicit nonzero maximum file and byte bounds, and set apply to opt into deletion. Publication and cleanup share a cross-process mutation lock and reload the durable index while locked, so a publication after preview invalidates the request before any deletion. Cleanup also re-verifies every retained object before applying the plan. It cannot address Primary, Mirror, backups, catalog records or remote APIs, and it cannot bypass the FDU-143 24-hour mirror hold. Corrupt retained cache state therefore blocks cleanup instead of risking loss.
