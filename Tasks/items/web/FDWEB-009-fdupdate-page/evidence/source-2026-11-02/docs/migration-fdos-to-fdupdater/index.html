Migrating FDOS to external FDUpdater

FDUpdaterFdosMigration converts the strict FDOS updater v1 configuration, current/previous slot metadata and idle engine state into a separate FDUpdater state root. It never edits or removes the FDOS root and never changes a service.

Create an administrator-owned request outside both roots:


{

  "schema": 1,

  "legacy_config": "ABSOLUTE_PATH_TO_FDOS_UPDATER_CONFIG",

  "state_root": "ABSOLUTE_NEW_FDUPDATER_STATE_ROOT",

  "instance_id": "fdos-installation-1",

  "architecture": "x86_64",

  "updater_identity": "FDUpdater.service",

  "application_identity": "FDOS.application"

}

Stop FDOS_Updater, then run the explicit migration:


FDUpdaterFdosMigration migrate --request ABSOLUTE_REQUEST_JSON

The destination must not exist. The command opens and exclusively locks the existing updater.lock; a running updater or a missing lock file blocks migration without creating or modifying legacy state. The command also rejects an active transaction, unknown fields or schemas, unsupported components/platforms, inconsistent configuration, invalid trust material and any slot whose executable does not match its size and SHA-256. It builds the complete destination in a sibling temporary directory and publishes it with one non-overwriting atomic move. A rejected or interrupted migration therefore leaves both the requested destination absent and FDOS_Updater unchanged.

The package contains:

  • fdupdater-registry.json with explicit fdos/server, fdos/agent and, when

    • configured, fdos/updater registrations using the original service names;

  • copied immutable current and previous executables plus their converted slot

    • metadata and retained FDOS artifact-signature domain;

  • one transaction.json per target with the legacy replay cursor and failed

    • sequence, but no active transaction;

  • fdos-trust.json containing only the legacy public verification keys;
  • fdos-compat.json retaining polling, CA, pause and local health-command policy;
  • fdos-migration.json, a deterministic receipt bound to the source config/state

    • hashes and migrated versions.

Application data remains at its existing path. Keep the complete legacy root and FDOS_Updater service definition until FDUpdater health and rollback have been verified by the deployment procedure. Service activation belongs to the installer and is deliberately outside the conversion command.

The later FDOS repository change should remove the in-process/workspace fdos-updater dependency and stop publishing application-owned updater commands. Its installer should provision FDUpdater independently, run this migration once, then switch the existing FDOS Server and Agent service ownership only after the migration receipt and FDUpdater health pass. FDOS UI actions should call the authenticated local FDUpdater API for status, check, apply, rollback, pause, resume and diagnostics using the fdos product and existing component names. If release publication temporarily keeps the strict FDOS v1 envelope, its compatibility provider must verify the retained original bytes in the distinct FDOS signature domain before giving normalized metadata to FDUpdater. The local state migration does not authenticate or authorize a new remote release. After rollout validation, FDOS can publish the product-neutral FDUpdate envelope and remove the legacy adapter in a separately versioned migration. The rollback procedure restores the original service definitions and legacy root without converting state back or deleting the FDUpdater package.
