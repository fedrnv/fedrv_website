Integrating software with FDUpdater

FDUpdater updates an application only after a local administrator registers an exact instance, product and component. Applications keep their own UI and business logic. They implement readiness and health through the public contracts and never add product branches to FDUpdater core.

1. Define stable target identities

Choose lowercase bounded product_id, component_id and per-install instance_id values. A multi-component installation uses one instance and product with separate component IDs. A single-binary product has one component. Keep executable versions separate from configuration, data, credentials, databases, workspaces and logs.

Use fdupdater_conformance::FixtureProduct and validate_matrix to validate the same identity and layout assumptions exercised by the reference products:


use fdupdater_conformance::{FixtureLayout, FixtureProduct, validate_matrix};



let products = vec![

    FixtureProduct::new("suite-a", "product-a", ["server", "agent"], FixtureLayout::MultiComponent)?,

    FixtureProduct::new("suite-b", "product-b", ["desktop"], FixtureLayout::SingleBinary)?,

    FixtureProduct::new("suite-c", "product-c", ["relay"], FixtureLayout::SingleBinary)?,

];

validate_matrix(&products)?;

# Ok::<(), fdupdater_conformance::ConformanceError>(())

2. Register only local authority

Create a TargetReceipt for each component. The receipt supplies the administrator-selected installation root, executable name, service binding, health policy, protected data roots and ownership identities. Release metadata cannot supply or widen any of these values. New targets default to the release channel; an authenticated local operator may set prerelease independently for an exact target.

The installation root and data directories must already exist and must not overlap FDUpdater state or another installation. Use process only for an explicitly supervised child process. Use the matching native service manager for production system services. A systemd or Windows service definition must execute the stable activation path <installation_root>/<executable_name> from its local receipt. FDUpdater atomically materializes the selected hash-verified slot at that path while the service is stopped, then starts the receipt-bound service. Service definitions, arguments and paths remain local administrator policy.

3. Publish the signed release contract

The unified release protocol is shared by the standalone service, embedded clients and FDUpdate Server.

Publish canonical fdupdate/release/v1 data inside fdupdate/signed-release/v1. Each artifact binds the target, platform, architecture, SemVer, HTTPS URL, size, SHA-256, compatibility, rollout, rollback and product-scoped signing key. hawkBit metadata and the standalone manifest provider carry the same signed envelope. Neither transport authorizes a release.

For private standalone delivery, use the runtime gateway provider together with target enrollment. The local target's persisted update_channel is sent on every check, including FDUpdater's own target, and is still enforced locally after the signed response arrives. Approval provides identity only; the server must separately grant the installation access to a repository. Removing either approval or that repository grant prevents new checks, downloads and reports.

Provision public trust keys locally. The runtime never receives a signing private key. A candidate must pass manifest and artifact signatures, replay cursor, channel, platform, architecture, updater-version, installed-version, component dependency, rollout and downgrade checks before staging.

Bootstrap each installation with its own identity

For a standalone target, set enrollment.installation_key_file to a protected file containing the 64-character reusable installation key. Keep the secret out of command arguments and ordinary configuration. code_file remains a mutually exclusive compatibility name for older one-time codes. FDUpdater creates and persists the installation's Ed25519 identity and exact signed request before the first network attempt. An interrupted or offline attempt therefore retries the same identity and consumes no additional server quota; deleting the protected state creates a new identity and consumes a new slot.

The key is attached only while the local enrollment has no authenticated server decision. After the first pending/approved/denied decision, later polling omits the bootstrap key. Update checks, package downloads and reports use only the installation-specific credential from the signed approval decision. A rejected or exhausted key returns the distinct EnrollmentError::Rejected; unavailability remains retryable without replacing the identity.

Embedded applications use fdupdater_enrollment::InstallationKey for their own protected file, stdin, or secret-input path. Its debug representation is always [REDACTED]. Each application instance opens EnrollmentClient with its own state root and instance ID, supplies the key only on the bootstrap request, and then passes the resulting client to fdupdater_app_mode. Reusing one bootstrap key does not share the local private key, instance ID, approval credential, update state or package cache.

Report managed FDUpdater liveness

An approved standalone FDUpdater creates ManagedUpdaterHeartbeat with EnrollmentClient::managed_updater_heartbeat. The client persists and increments the heartbeat sequence before returning the signed document, so a restart or an uncertain network result cannot reuse a sequence. It signs the instance ID, updater version, send time, sequence and random nonce with the same installation Ed25519 identity used for enrollment.

Send the document to POST /v1/updater/{tenant}/{product}/heartbeat with the installation credential as Authorization: Bearer ... and the exact instance ID in X-FDUpdate-Instance. The server requires current approval, matching scope and identity, a valid signature, a bounded timestamp and a sequence greater than the last durably accepted value. A duplicate or older sequence returns 409; invalid credentials, signatures, scopes and revoked identities fail authorization. Liveness is derived from the server receive time. A stale heartbeat is an observation state and never authorizes a release or reports an update failure.

Bind the applications managed by an updater

Approval, heartbeat and repository access do not implicitly give an FDUpdater authority over an application. Using the private operator API, bind the approved updater instance to each exact product/component, repository, platform, architecture and locally selected release channel. Grant check and update separately. Check-only bindings can report installed versions and health but receive no assignment or package.

Binding changes use an expected revision. The first bind uses revision zero; every later bind uses the revision returned by the installation inventory. Unbind disables the policy and advances its revision, so a delayed prior request cannot silently restore authority. The server rechecks the current binding and repository grant during check, package download and result reporting. Revocation, repository removal, channel change or unbind therefore takes effect without rewriting existing assignments.

4. Implement readiness and health

An application that must quiesce implements the authenticated loopback readiness protocol. It stops accepting work, checkpoints active work, flushes durable state, releases exclusive resources and then returns ready. It may return bounded defer_until or reject; timeout and disconnect fail closed.

An Agent supervised by the watchdog implements the authenticated heartbeat protocol. FDUpdater applies a bounded restart budget, exponential backoff and durable quarantine. Diagnostic profiles list exact approved log and crash-metadata paths beneath receipt-owned data roots. Secrets, command arguments and environment-bearing lines must be redacted before persistence or upload.

5. Preserve recovery behavior

Activation stages verified immutable bytes, atomically advances current/previous pointers and performs a bounded health check. Failure restores the previous verified slot. The privileged rollback action uses only a strictly older, hash-verified local previous slot, preserves the replaced current slot, and does not poll or apply a pending provider release. A general downgrade requires a signed authorization bound to the exact installed version. FDUpdater self-update uses the same trust and channel resolver and hands the staged candidate to the independent bootstrap.

6. Run the conformance kit

From a checkout using the supported Rust toolchain:


cargo test -p fdupdater-conformance

cargo test -p fdupdater-conformance --test isolation

The suite proves three unrelated product layouts, mixed versions, simultaneous offers, Linux and Windows contract selection, rollback, server unavailability, per-target channels, readiness decisions, watchdog restart/quarantine, redacted incidents and cross-target isolation. The native activation portion runs on the current host; run it once on each supported operating system before releasing an integration.
