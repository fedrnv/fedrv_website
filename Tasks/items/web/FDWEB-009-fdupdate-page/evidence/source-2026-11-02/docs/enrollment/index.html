Installation enrollment

Each installed application instance has its own Ed25519 identity. FDUpdater generates the key inside its protected local state root, persists it with private-file permissions and sends only a signed enrollment request containing the instance ID, public key and random nonce. Reopening the same instance reuses that identity and the exact pending request; a different instance receives a different key.

The enrollment authority returns a canonical signed decision bound to the request digest, instance and public key. FDUpdater accepts strictly increasing revisions and exposes four states: pending, approved, denied and revoked. A revoked identity cannot return to another state. Approval credentials remain inside the protected signed state and are never returned by status, CLI output or audit records.

Only approved returns a credential, and only for a target explicitly assigned in the decision. Anonymous, pending, denied, revoked and wrong-target requests fail closed before a metadata or artifact transport can be called. Authority unavailability uses a bounded retry count and retains the same signed request.

Installation Account authorization

An installer may authorize the signed software identity with an enabled Installation Account ID or email, its current password, and the exact non-empty set of private repositories requested by the installed software. The request is schema-versioned and sent to the normal product enrollment endpoint. The account must currently grant every requested repository; the server never expands the set from the account's other grants.

The human password exists only in zeroizing request memory and is not written to FDUpdater state, registry state, logs, audit, or the issued installation credential. The account is re-read and authenticated while its durable shared lock is held through the registry decision. Registration quota is counted by distinct signed instance identity; concurrent attempts cannot overrun it.

An identical pending identity is approved with the durable outcome performed_with_installation_account, retaining its earlier submission audit. An exact retry returns the same signed decision without consuming quota. A changed repository set, insufficient grants, wrong password, disabled account, exhausted quota, or revoked identity fails closed. Each successful installation receives its own credential and does not retain the Installation Account password.

Installation keys

An operator can issue a reusable installation key for one product/component with an exact positive registration limit. The server persists only a domain-separated SHA-256 verifier, a non-secret key ID, expiry and disable state, the current repository allowlist, and a ledger of distinct installation instance IDs. The plaintext key is returned only by the issuance response.

Each redemption still carries the installation's own signed Ed25519 enrollment request. A retry of that exact identity is idempotent and does not consume another slot. A different identity consumes one slot, remains pending, and needs normal operator approval. Once the limit is reached, concurrent new identities fail closed. Expiry and disabling stop new identities while preserving idempotent retries and the historical ledger; denial, revocation, or uninstall does not refund a slot.

The operator endpoints are:

  • POST /v1/operator/installation-keys to issue a key with

    • max_installations and allowed_repositories;

  • POST /v1/operator/installation-keys/list to return verifier-free key status

    • and usage counts;

  • POST /v1/operator/installation-keys/update to change the future admission

    • limit/disable state, repository allowlist, or the separate existing-update suspension flag.

The earlier /v1/operator/enrollment-codes issuance route remains compatible and defaults omitted policy fields to a limit of one and an empty repository allowlist. Schema 1 and 2 registry snapshots migrate consumed one-time codes to a one-entry ledger without increasing their access.

Applications can keep their existing UI and read the state through the authenticated local API or CLI:


FDUpdater enrollment --endpoint 127.0.0.1:PORT --credential-file ABSOLUTE [--instance INSTANCE_ID]

The result contains the instance ID, public-key fingerprint, state and decision revision. It contains no private key or approval credential. Enrollment transitions use the structured audit adapter and must be recorded before an approval is committed.

Registration audit

The device gateway atomically persists one redacted event for each distinct registration outcome: pending, denied, approved replay, administrator approval, Installation Account performance, or an unavailable delegated authority. Exact retries are idempotent. Events contain the request digest, outcome provenance, tenant, product, components, complete repository set, optional Installation Account ID, software instance, sequence, and server time. Passwords, installation keys, bearer credentials, signed decisions, email addresses, and request bodies are never stored in this audit.

The authenticated gateway query is POST /v1/operator/registration-audit/query. It accepts bounded time, outcome, product/component, repository, Installation Account ID, instance, and page filters. The caller must supply its complete repository allowlist. An event is visible to a repository-scoped caller only when every repository on the event is within that allowlist; a manipulated repository filter returns no rows. Unscoped events are reserved for the owner view.

The web administration table is /admin/registration-audit. It derives the allowlist from current administrator roles, revalidates every gateway row, uses 25-row pages, and returns Cache-Control: no-store. There is deliberately no CSV or other export route: out-of-scope filters are denied before the gateway is queried, and partial-scope results are never rendered.

The server-facing protocol conformance and denied-state matrix run with:


cargo test -p fdupdater-enrollment

cargo test -p fdupdater-enrollment --test denied_states

cargo test -p fdupdate-device-gateway
