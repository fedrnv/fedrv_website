Client feedback

Integrated applications use fdupdate-feedback to create feedback or bug reports and keep a bounded durable retry queue. The application supplies its own current target and installed version from the same local receipt/registry it uses for update checks. It never accepts an installation ID, tenant or repository from the user. The gateway derives those values from the authenticated installation credential and its last reported application state.


use fdupdate_feedback::{FeedbackKind, FeedbackQueue, FeedbackRequest};



# fn example(state_root: &std::path::Path, target: fdupdate_contract::Target,

#            installed: fdupdate_contract::Version) -> fdupdate_feedback::Result<()> {

let request = FeedbackRequest::new(

    "ui-20261018-0001",

    target,

    FeedbackKind::Bug,

    "Window does not open",

    "Opening the main window leaves the process in the background.",

    1_792_300_000,

    installed,

    None, // diagnostics require an explicit Some(...)

)?;

FeedbackQueue::open(state_root)?.enqueue(request)?;

# Ok(()) }

A transport submits the oldest queued request as JSON to POST /v1/feedback/{tenant}/{product} with the installation credential as Bearer authorization and X-FDUpdate-Instance. submit_next removes a request only after the transport accepts it and the shorter queue is durably committed. A transient outage leaves the original request ID and submitted version intact for an idempotent retry.

The request is limited to a 160-byte subject, 8 KiB body, three explicitly opted-in text diagnostics, 16 KiB per diagnostic and 32 KiB total diagnostic text. Diagnostic labels are basename-only. Both the client constructor and server store redact complete lines containing authorization, password, secret, token or credential markers. The adapter never reads host files automatically.

The server authenticates the installation and component, requires prior reported installed state, and records the client-reported version beside the server's last-known installed version. It labels them match, mismatch or unknown and never substitutes an assigned or available release. Tenant, installation, repository, platform, architecture and channel are server-derived. A changed reuse of a request ID conflicts; an exact retry returns accepted: false. New reports are limited to 20 per installation per hour and the durable store is bounded to 100,000 records.

The client request ID is idempotency provenance within one installation. On first acceptance the server derives a separate stable report ID from the tenant, product, installation and client request ID. Operator URLs, workflow mutations, duplicate links and audit use that server report ID, so two installations may safely choose the same client request ID. Current gateway and feedback snapshots require their feedback section and every workflow field. Explicit schema-1 migration derives the same stable IDs and rejects ambiguous legacy duplicate links; malformed current snapshots fail before state becomes visible.

HTTP responses use 401 for invalid/revoked identity, 409 for missing installed state or changed duplicate, 429 for the per-installation rate limit, 507 for exhausted durable capacity and 503 when the atomic gateway snapshot cannot be committed.

Administrator inbox

Owners, fleet operators and security administrators open /admin/feedback. The server requests only products represented by repositories visible to the account and filters each report again by its server-derived repository. The inbox supports bounded search, status/type filters and 25-record pages. Report details link to the exact installation and repository and keep the original reported version beside the current server-last-known version.

Workflow changes use the stable server report ID, the report's current revision and the administrator session CSRF token. New, In progress, Resolved and Closed status, internal notes and same-repository duplicate links persist in the gateway snapshot. A stale revision returns conflict. Original subject, body, version, identity, timestamps and diagnostics never change; every workflow mutation appends actor/time/status/note metadata to a bounded audit trail. Restoration reconciles each note with exactly one audit revision, enforces ordered server timestamps and rejects self-links or duplicate cycles. All client text, diagnostic names/content and note text are HTML-escaped. The page uses Cache-Control: no-store and switches filters and workflow controls to one column below 600 px.
