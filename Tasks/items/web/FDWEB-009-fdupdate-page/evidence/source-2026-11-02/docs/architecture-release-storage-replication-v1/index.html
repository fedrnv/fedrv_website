FDUpdate release storage architecture — primary S3, future mirror, VPS latest-copy cache

Status: owner-approved target architecture; implementation and live migration not started.

Storage tiers

1. Primary: Hetzner Object Storage S3 or compatible alternative; immutable content-addressed artifacts and signed manifests for every retained release and prerelease. 2. Secondary: independent S3 mirror (prefer distinct provider/region and failure domain), planned but not deployed now; eventually replicate all retained versions, with verified object checksums and delayed/versioned deletion protection. 3. Local VPS: verified latest stable release and latest prerelease per product, channel, OS, architecture and required package variant, not just one global file. VPS copies are both recovery cache and last-known-good fallback; reserve sufficient disk and capacity alerts.

Publication and activation

  • CI manual publish uploads to Primary, validates digest/size/signature and commits immutable catalog metadata.
  • Stage the new latest package to VPS and verify it before evicting prior local copy; maintain at least one previously known-good candidate during replacement.
  • Define clear readiness semantics: publishing a release may be blocked or marked degraded if latest VPS copy is not safely present; never claim three replicas before mirror activation.
  • When mirror is enabled, asynchronous replication has tracked pending/verified/failed states and alerts. Never infer successful mirror write from a queued job.
  • Manifest/catalog metadata, encryption/signing keys, installation registry and DB require separate backup and restore, not merely artifact copies.

Download and failure

  • Primary direct download with short-lived authorized URL for private artifacts; fallback to independently verified Mirror when enabled.
  • If both S3 locations unavailable, latest local VPS copy can be served through authenticated FDUpdate gateway with strict bandwidth/concurrency/rate limits.
  • Older versions are unavailable during primary outage until mirror is enabled; avoid claiming always-on service: VPS/network/API are shared failure domains.
  • Every fallback verifies exact immutable artifact digest and signed manifest; no downgrade or private-to-public disclosure.
  • Health checks, reconciliation, periodic scrub, orphan cleanup, corruption quarantine and restore drills.

Retention and deletion

  • Configurable stable/prerelease retention per repository (default 10 each from existing requirements).
  • Pin latest local variants and all objects required by active rollout/rollback; stage replacements atomically.
  • Mirror deletion must not blindly propagate accidental primary deletion; use object versioning or protected deletion grace and restore process.
  • Account for VPS local disk, primary/mirror storage, egress, request charges and API proxy costs.

Proposed FDTasks successor scope

  • Storage provider abstraction and S3 backend.
  • Atomic primary publication and local latest-copy cache.
  • Fallback download selection, integrity and access control.
  • Mirroring interface and replication journal (future mirror inactive).
  • Scrub, retention, metadata backups, restore and failure tests.
  • Admin dashboard showing replica health, cache occupancy, per-release copies, alerts and costs.
  • One targeted gate and independent review under a next development Epic; avoid modifying accepted D009 task specs and follow FDTasks 5.5 append-only rules.

No production DNS, S3 credentials, live releases or billing changed by this document.

Owner-approved 24-hour delayed mirror and database backup policy (2026-10-18)

  • VPS holds the live database. Create consistent, encrypted, restorable database backups in Primary S3, including required catalog, enrollment and installation metadata; replicate backups to Mirror S3.
  • Every mirror mutation (create, overwrite where permitted, and delete) executes no earlier than 24 hours after the corresponding primary operation has been durably confirmed and validated. Queue an immutable operation record with source object version/digest, primary confirmation timestamp and mirror-not-before timestamp.
  • At execution time revalidate source object version, cryptographic digest, authorization, retention pins and current deletion eligibility. Stale or superseded operations must be cancelled/reconciled, not blindly replayed.
  • Mirror deletes require verified primary deletion eligibility and independent second check after the full delay; do not delete the last known restorable database backup or protected release.
  • The delay applies to new backups as well: mirror recovery point may be at least 24 hours behind primary. Protect this window with Primary S3 object versioning/immutability and local database WAL/snapshot retention; do not advertise zero data loss.
  • A 24-hour delayed mirror is a replication target, not a complete backup defense against ransomware or credential compromise. Use separate credentials, versioning/Object Lock where supported, restore drills and tested offsite recovery.
  • Monitor replication queue age, lag, failed verification, backup age, restore success and retained storage size. Make the delay configurable only through a future explicit policy change; initial mandatory minimum is 24 hours.
  • No live mirror is provisioned in this phase; preserve interfaces and migration plan.
