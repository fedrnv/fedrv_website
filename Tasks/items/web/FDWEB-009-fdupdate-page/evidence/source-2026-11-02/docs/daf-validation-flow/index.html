DAF validation publication and update flow

DAF source revision 09ea5125e2a55f21bd231fd077d5cc8a7c2d7b9b adds an opt-in publish_fdupdate_validation input to its existing manual build workflow. The job runs only after the application build and persistence jobs succeed, uses the protected fdupdate-validation environment and requests id-token: write. It prepares exact publication plans locally in the job and submits a Linux x86-64 DAF application package and the checked-in BAW master firmware package to separate publisher IDs.

The validation server must register these publishers with the same exact GitHub issuer, repository fedrnv/DAF, workflow ref fedrnv/DAF/.github/workflows/daf.yml@refs/heads/main, environment fdupdate-validation, main ref, audience fdupdate-server and workflow_dispatch event:

  • daf-application: product daf, component application, target linux/x86_64.
  • daf-baw-master: product daf, component controller-firmware, target linux/baw-master.

The protected environment variable FDUPDATE_PUBLISH_URL must be a credential-free HTTPS origin. The workflow obtains its short-lived OIDC token from the GitHub runtime, submits it only in the Authorization header and unsets the shell value after both requests. Plans bind the DAF Git commit, workflow recipe digest, versions, sizes and SHA-256 artifact digests. The server signs and commits each release independently; a wrong firmware architecture such as hsd-master is outside the publisher scope.

The DAF application keeps its existing update dialogs and BAW firmware mechanism. An enrolled installation remains unable to check or download while pending. After explicit approval, the application assignment targets daf/application and the firmware assignment targets daf/controller-firmware; the BAW master identity is carried by publication compatibility/architecture metadata. Reports use the accepted application-managed flow and are idempotent.

The Linux validation foundation is installed on the dedicated server at update.fedrv.de with a trusted public TLS edge. Only the exact publisher ingestion path is public; hawkBit Management and operator boundaries remain private. Hardware acceptance requires an accessible supported BAW master controller; simulator results are not hardware evidence.
