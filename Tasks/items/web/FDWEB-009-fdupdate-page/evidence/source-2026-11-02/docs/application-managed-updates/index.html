Application-managed updates

Application-managed mode lets an existing application keep its UI, installer, restart policy and recovery behavior. FDUpdater supplies a versioned Rust check/package/report contract through fdupdater-app-mode; it never receives an application install path and writes packages only below its protected state root.

The application first creates an ApplicationCheckRequest with its installation identity, target, platform, architecture, channel, updater version and installed component versions. ApplicationUpdateService::check accepts remote metadata only through the same approved enrollment gate used by ordinary updates. Its response contains the assignment ID, display version, signed size and digest, release cursor and the exact SignedRelease supplied by the assignment service. The service verifies the release signature, artifact signature, target, compatibility, rollout and release channel before persisting or returning that response.

prepare_package streams the assigned bytes into a bounded temporary file below application-packages, checks the signed size and SHA-256 digest, and atomically caches the verified package. open_package returns a read-only VerifiedPackage stream for the exact assignment after rechecking current enrollment approval and the signed release. The host application copies that stream into its own installer or staging flow. FDUpdater does not modify the application tree, run the installer or restart the application in this mode.

For lightweight self-update without the FDUpdater daemon, implement ApplicationSelfUpdateHost. The library passes only a PackageDescriptor and the already verified VerifiedPackage stream to the host's stage callback. stage_application_update must leave the running installation unchanged and returns an opaque host-owned prepared value. activate_application_update then invokes the host's external restart helper and health check; restart failure, health failure or an unhealthy result invokes rollback_and_restart before an error is returned. rollback_application_update exposes the same exact host rollback for an explicit user action.

The host owns installation paths, atomic replacement and durable recovery for its opaque prepared value. A self-updating process should execute restart and recovery from its installer or a small external helper so interruption cannot leave the running executable half-replaced. The host must preserve the previous verified version until health succeeds. No path, command or helper identity comes from release metadata. A statically linked library is updated only by staging and restarting a newly built owning application; the SDK does not hot-swap library bytes.

After its own installation flow, the application sends an ApplicationReportRequest for the same assignment. An installed result must name the assigned version and requires a previously verified package. failed and deferred results may include a bounded, non-control-character detail for the remote service, while structured audit events contain only the assignment, target, phase, version and outcome. An identical report is idempotent; a conflicting second report is rejected.

Anonymous, pending, denied, revoked and wrong-target identities are rejected before metadata or artifact transport. Approval is checked again for package access and reporting, so later revocation also fails closed. Network retries are explicitly bounded. Invalid signatures, expired or replayed releases, corrupt packages and locally altered assignment metadata are rejected.

Operators can inspect the non-secret local status through the authenticated, read-only loopback API or CLI:


FDUpdater app-updates --endpoint 127.0.0.1:PORT --credential-file ABSOLUTE [--instance INSTANCE_ID]

The result exposes assignment ID, local target, version, phase and final outcome. It excludes enrollment credentials, signed metadata, report detail and package paths.

The server-facing contract fixture and denial matrix run with:


cargo test -p fdupdater-app-mode

cargo test -p fdupdater-app-mode --test denied_states
