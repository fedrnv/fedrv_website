FDOS updater baseline inventory

This inventory covers the immutable snapshot in legacy/fdos-updater/. The source is fedrnv/FDOS commit 1013672a9d667b4b65b8205dd455d67fc18d6152. The snapshot contains 53 source-derived files plus the FDUpdate-owned MIGRATION.md provenance note. Each source-derived Git blob matches that commit.

Reproduction

The imported directory is intentionally not a complete Cargo workspace. Its root manifest still names scripts/xtask, which was not imported, so invoking Cargo against legacy/fdos-updater/Cargo.toml fails while loading the workspace. Do not repair that historical snapshot.

Use a detached checkout of the exact source commit to verify both the imported blobs and the applicable updater/distribution tests:


git clone --filter=blob:none --no-checkout https://github.com/fedrnv/FDOS.git ../FDOS-baseline

git -C ../FDOS-baseline checkout --detach 1013672a9d667b4b65b8205dd455d67fc18d6152

node scripts/verify-fdos-baseline.mjs --source ../FDOS-baseline

The command requires Git, Node.js, rustup and toolchain 1.98.0. It first compares all 53 source-derived blobs, then runs this locked package set on the full source checkout: fdos-release-format, fdos-install-layout, fdos-updater, fdos-release-publisher and fdos-release-store, including all targets. Use --integrity-only when only the import check is required.

FDOS coupling that must not enter the generic core

  • The public contract has a closed Component::{Server, Agent, Updater} enum,

    • FDOS-prefixed binary/service names, /opt/fdos examples and a /fdos release URL prefix.

  • One config owns one root and at most one target of each fixed component. The new

    • registry must support unrelated products, multiple independently versioned components and non-overlapping validated roots.

  • CLI parsing, artifact filenames, release publication plans and service scripts

    • derive authority from the fixed component enum. New remote metadata may identify a registered target but cannot add a local path, command or service name.

  • Updater readiness is a host nonce/process record. Application update readiness,

    • quiescence, watchdog restart budgets and incident reporting are new contracts; they cannot be inferred from the historical health command.

  • Historical semantic versions and the FDOS manifest cursor are compatibility

    • inputs. Release/prerelease policy becomes persisted per-target state and cannot permit an implicit downgrade.

Invariants retained by migration

  • Ed25519 signatures remain domain-separated and cover exact manifest/artifact

    • identity; invalid signatures, hashes, replay, expiry, downgrade and incompatible updater versions fail closed.

  • Downloads, JSON, logs, commands, retries, health checks and recovery are bounded.

    • HTTPS redirects and ambient proxies remain disabled where they could change the authenticated endpoint.

  • Executables remain immutable hash-addressed slots with atomic current/previous

    • pointers, an OS-held mutation lock and a durable recovery journal.

  • Configuration, credentials, application data and workspaces remain outside

    • executable slots. Only receipt-bound targets inside validated installation roots can be stopped or mutated.

  • Self-update keeps a stable bootstrap, fresh readiness proof, bounded handover and

    • local restoration of the previous updater without depending on an application or update server.

  • Runtime services never receive release signing keys. Publication stays manually

    • initiated and published artifacts remain immutable.

Verification boundary

The reproduced package suite proves the portable Windows behavior exercised by the selected Rust tests and loopback TLS fixtures. It does not prove Linux native service behavior, reboot survival, production identities, real systemd/polkit, hosted publication or production signing. Those checks remain assigned to their implementation tasks and the Epic full gate. The historical Node native scripts were inventoried but were not executed as FDU-001 acceptance because they mutate native services and require task-specific fixtures and privileges.
