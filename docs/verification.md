# Local verification

All acceptance commands run locally. Use Node/npm versions in the root README, `npm ci`, then `npm run check` and `npm run build`. The build is static only and does not execute tests or deploy. With `npm run preview` running in another terminal:

```sh
npm run verify:bootstrap
npm run verify:content
npm run verify:site
npm run verify:home
npm run verify:accessibility
npm run verify:browser
```

Select the commands belonging to the task being verified; the complete foundation gate uses this set. Content tests build isolated fixtures outside `dist/`. `verify:site` inspects every generated HTML head, route, fragment and asset reference, verifies unique titles/descriptions/canonical URLs and Open Graph tags, checks sitemap and robots, and allows only the bundled local language module and its EN/DE/RU JSON dictionary. It checks local destinations; external destinations require separate source and link review.

For the foundation integration gate, also run `npm run verify:clean`. It copies the exact source/configuration/assets into an owned disposable directory without dependencies or build caches, verifies matching SHA-256 hashes, then runs clean install, type checking, build, bootstrap and metadata/link checks there. It checks the source did not change while testing and writes a compact manifest to `.local/clean-verification.json` before removing the snapshot. It never copies credentials or the `.git` directory. The gate must also run the content and browser checks above against that same source candidate. No command here is a hosted workflow stage.

The browser commands use an installed Chromium executable and isolated temporary profiles (see root README). Accessibility checks run axe WCAG A/AA and best-practice rules for all five routes in English, German and Russian at 360/1440px, check heading sequences and visible keyboard focus. They do not establish certification. Browser screenshots need human/model visual inspection. Use `FDWEB_ROUTES=/,/404,/update,/cot,/storage` to capture every route, and `FDWEB_SCREENSHOTS` for a task-specific output directory.

Manual checklist: Tab to the skip link, press Enter and confirm focus reaches main; continue through navigation, cards and project/portal links; verify visible focus, descriptive link names and expected destinations. At 360px and desktop, inspect readable text, heading order, clipped/overflowing content and image fallback. Decorative product icons have empty alternatives next to names; content images require meaningful alternatives. Request an unknown URL and confirm the server returns the 404 page with HTTP 404. `404` is noindex and excluded from sitemap.

The site uses a four-color theme, system fonts and no animation or tracking. Its only visitor script selects and switches interface language. Run `npm run verify:languages`, `npm run verify:brand` and `npm run verify:portal` for the current multilingual portal contract. The Open Graph card is a real local 1200×630 PNG generated by `npm run generate:social` with the installed browser; inspect it after regeneration. No product screenshot is invented.

For local CLI checks, PowerShell uses `npm.cmd` if needed. Set `FDWEB_GIT` when running the separate task-ledger checks if Git is outside PATH. Do not run `npm ci` while Astro dev/preview is running on Windows: stop those owned processes first so native modules can be replaced.

Run `npm run verify:browser-lifecycle` to check startup failure, original callback-error preservation and normal shutdown. Browser liveness accounts for both exit codes and signal termination, and cleanup never issues a kill for a missing/exited process. Run clean/content build checks before the browser checks, then run browser commands sequentially to keep host resource use bounded. A failed gate remains failed until the correction and affected verification have passed.
